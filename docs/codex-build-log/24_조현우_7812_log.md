## 2. 프로젝트에서 Codex를 사용한 방식

팀원은 “코드를 알아서 만들어 달라”는 한 줄 요청에 그치지 않고 다음 방식으로 Codex와 반복했다.

1. 문제와 현재 제약을 프롬프트에 명시했다.
2. 모호한 제품 범위는 먼저 비교·반박·추천을 요청했다.
3. 합의한 계획은 구현 항목, 공개 인터페이스, 테스트, 완료 조건까지 구체화해 다시 위임했다.
4. Codex가 코드를 변경한 뒤 lint, build, 단위 테스트, 브라우저, Docker, CloudFormation, 실제 AWS 상태를 확인하게 했다.
5. 오류가 나면 로그 전체를 다시 전달하고 “왜 실패했는지” 진단과 “수정해줘” 구현을 분리했다.
6. 로컬 성공을 배포 성공으로 포장하지 않고, 현재 확인 가능한 경계와 남은 작업을 기록했다.

### 3.4 RAG를 “벡터 DB가 있다”가 아니라 생성 근거로 설계하기

**문제**

“FastAPI가 DB를 검색하고 필요한 내용만 OpenAI API에 전달하는 것이 정말 RAG인가?”, “서비스 DB와 RAG DB는 같아야 하는가?”라는 구조적 질문이 있었다. 동시에 HikerAPI와 외부 Instagram 데이터를 대회용으로 사용할 때의 권리·품질 위험도 있었다.

**대표 프롬프트**

> FastAPI → RAG DB 검색 → 필요한 자료만 선별 → OpenAI API 호출, 이게 정말 RAG DB를 활용한 LLM이라고 할 수 있나?

> 외부 데이터셋을 StoryCard용 RAG DB로 사용할 수 있을까?

**계획과 결정**

- 검색(Retrieval), 문맥 추가(Augmentation), 생성(Generation)의 책임을 FastAPI와 OpenAI 사이에 명확히 나눴다.
- 모델이 DB에 직접 접속할 필요는 없으며, 서버가 private DB에서 근거를 고른 뒤 최소 문맥만 전달하도록 했다.
- 동일한 PostgreSQL 클러스터 안에서도 개인 기억과 외부 패턴을 논리적 테이블·메타데이터·접근 규칙으로 분리했다.
- HikerAPI는 대회 제출이라는 목적만으로 이용 조건이 사라지지 않으므로, 서면 권리 확인 전 운영 수집을 하지 않기로 했다.

**데이터셋 검증과 결과**

제공된 인플루언서 데이터 58건에 대해 체크섬, 중복, 순위, 숫자 범위, 결측률, 출처 분포를 검사했다. 프로필 탐색용 구조화 검색에는 쓸 수 있지만 Storylog가 필요로 하는 훅, CTA, 콘텐츠 구조, 목적, 정규화 성과, 레코드별 권리 근거가 없어 “포맷 패턴 RAG”의 직접 재료로는 부족하다고 결론냈다.

### 3.5 Google 로그인 400 오류를 브라우저에서 재현하기

**문제**

프론트엔드에서 Google 로그인을 누르면 400 오류가 발생했다. 단순히 키를 다시 만들라고 안내하면 원인을 확인할 수 없었다.

**대표 프롬프트**

> 프론트엔드 실행해서 구글 로그인 시도하니까 400 에러 뜨는데?

**진단과 복구**

- 로컬 프론트에서 초대 코드부터 Google 로그인까지 직접 재현했다.
- 프론트와 백엔드의 인증 URL 생성은 모두 200임을 확인했다.
- Google 오류 상세의 요청 URI를 확인해 원인이 `redirect_uri_mismatch`임을 특정했다.
- 현재 구현은 Cognito가 아닌 FastAPI 직접 callback 방식이므로 Google OAuth 웹 클라이언트에 다음 URI를 정확히 등록하도록 정리했다.
  - `http://localhost:8001/api/auth/google/callback`
  - `http://localhost:8001/api/calendar/callback`

**교훈**

기획 단계에서 추천했던 Cognito 구조와 실제 구현의 FastAPI callback 구조가 달라질 수 있으므로, 일반적인 콘솔 안내보다 실행 중인 요청 URI를 기준으로 설정값을 검증해야 했다.

### 3.6 사진 업로드 실패에서 private S3 설계까지

**문제**

사용자가 사진을 선택해도 업로드가 된 것처럼 보이지 않았고, DB에도 asset이 없었다. 로컬 파일은 컨테이너의 `/tmp`에 저장돼 재시작 시 사라질 수 있었으며 운영 S3는 인프라만 있고 애플리케이션과 연결되지 않았다.

**대표 프롬프트**

> 사진 업로드가 제대로 되지 않는 것 같아. 로컬이라 그런가? 어디에 저장돼?

> 추천하는 방식으로 진행해서 사진 업로드에 문제가 없게 해.

**계획과 구현**

- 로컬에서는 multipart 업로드를 명시된 storage directory에 저장한다.
- 운영에서는 백엔드가 소유권이 포함된 object key와 짧은 presigned PUT URL을 발급한다.
- 프론트가 S3로 직접 전송한 후 finalize API가 크기·MIME·소유권을 검증한다.
- DB에는 만료되는 URL이 아니라 bucket/key를 저장하고, 읽을 때만 presigned GET URL을 발급한다.
- 성공한 파일은 `pending/`에서 private `records/`로 승격하고, 실패·미완료 파일은 수명 주기로 정리한다.

**UI 반복 수정**

파일명만 표시하던 화면에 이미지 미리보기, 업로드 진행 상태, 허용 형식·개수·크기 검증, 사용자가 조치할 수 있는 오류 메시지를 추가했다.

**검증**

- fake S3를 사용한 presigned upload 통합 테스트
- 실행 중인 로컬 컨테이너로 실제 PNG 업로드
- 레코드가 `MEDIA_PROCESSED`에 도달하고 DB에 photo asset과 원본 파일명이 저장되는지 확인
- 테스트 레코드 삭제와 관련 파일 정리 확인

### 3.7 AWS 배포 실패를 한 단계씩 복구하기

**초기 목표 프롬프트**

> Amplify(Next.js) → ECS Express(FastAPI) → RDS PostgreSQL로 구성하고, main 변경 시 GitHub Actions가 테스트·이미지 빌드·배포·검증까지 자동 수행하게 해줘. 장기 AWS access key 대신 GitHub OIDC를 사용하고 싶어.

**구현 계획**

1. Bootstrap: GitHub OIDC와 배포·CloudFormation 실행 역할
2. Platform: VPC, private RDS, ECR, private S3, Secrets Manager, IAM
3. Service: ECS Express, 상태 확인, CloudWatch
4. CI/CD: 테스트 → immutable image → stack 배포 → 실제 endpoint smoke test

**오류 1 — GitHub가 AWS 자격 증명을 받지 못함**

- 현상: `Credentials could not be loaded`가 12회 재시도 후 실패했다.
- 진단: workflow의 `production` GitHub Environment 때문에 OIDC subject가 environment 형식으로 바뀌었지만 AWS trust policy는 main branch subject만 신뢰했다.
- 수정: Environment 의존을 제거하고 저장소·main branch로 제한된 immutable repository subject를 사용하도록 trust policy와 문서를 고쳤다.
- 검증: Bootstrap `UPDATE_COMPLETE`, OIDC 역할 assume 허용 확인.

**오류 2 — 첫 RDS 생성 시 service-linked role 권한 부족**

- 현상: Platform stack이 `ROLLBACK_COMPLETE`가 됐다.
- 진단: 신규 계정에 `AWSServiceRoleForRDS`가 없고 CloudFormation 역할에 생성 권한이 없었다.
- 수정: `rds.amazonaws.com`과 정확한 RDS service-linked role ARN에만 제한한 최소 권한을 추가했다.
- 복구: 실패 stack과 그 stack이 보존한 “버전이 0개인” 빈 Runpod secret만 소유 관계를 확인한 뒤 정리했다.
- 검증: IAM simulation 허용, Bootstrap update 완료, 재시도 가능한 clean state 확인.

**오류 3 — 암호화 RDS의 KMS grant 부족**

- 현상: RDS 관리형 키는 생겼지만 DB 생성이 다시 실패했다.
- 진단: CloudFormation 실행 역할의 `kms:DescribeKey`, `kms:CreateGrant`가 implicit deny였다.
- 수정: 같은 계정의 RDS/Secrets Manager 경유 요청과 AWS resource grant에만 적용되는 최소 KMS 권한을 추가했다.
- 검증: RDS 경유 권한은 allowed, EC2 경유 grant는 implicit deny임을 확인했다.

**오류 4 — Docker Hub 일시적 502**

- 현상: CI가 `python:3.13-slim` manifest 조회 중 `502 Bad Gateway`로 실패했다.
- 진단: 애플리케이션이나 Dockerfile 오류가 아니라 외부 registry의 일시 장애였다.
- 대응: 진행 중인 AWS 배포와 중복 실행하지 않고 실패한 CI job만 재실행하도록 구분했다.

**오류 5 — 첫 ECS Express 생성과 immutable image 재시도**

- 현상: ECS service-linked role을 즉시 assume하지 못해 Service stack이 rollback됐다.
- 진단: 역할은 곧 정상 생성되었고 AWS 관리형 Express 인프라 정책에도 필요한 권한이 있어, 지속적 권한 누락이 아니라 최초 생성 직후 IAM 전파 시점 문제로 판단했다.
- 수정: 불필요한 광범위 권한을 추가하지 않고 실패한 Service stack만 정리했다. 동일 commit 재시도 시 immutable ECR tag를 덮어쓰지 않고 기존 이미지를 재사용하도록 workflow를 idempotent하게 만들었다.
- 검증: Platform `CREATE_COMPLETE`, Service 재생성 성공, 배포 image digest 일치 확인.

**현재 실제 배포 검증**

- ECS Express Service stack: `CREATE_COMPLETE`
- Platform/RDS stack: `CREATE_COMPLETE`
- 배포 이미지 tag: `b8ad3ce9fe611406f12b43ae5113147abdb5e444`
- `GET /health`: `{"status":"ok"}`
- `GET /ready`: PostgreSQL `ok`, Redis `not_configured`
- 운영 Redis는 의도적으로 필수 의존성에서 제외했다.
- Amplify 앱은 아직 생성되지 않아 공개 프론트엔드 URL은 없다. 따라서 “전체 공개 배포 완료”라고 주장하지 않는다.

### 3.8 잘못된 아키텍처 이미지도 수정 대상으로 남기기

처음 생성한 시스템 아키텍처 이미지는 결제·메일·모바일·큐·운영 Redis가 포함된 일반 웹 서비스 도식이어서 실제 Storylog와 맞지 않았다. 사용자가 “우리 시스템이랑 안 맞지 않아?”라고 지적했고 Codex도 이를 인정했다. 이후 실제 구성인 Amplify/Next.js, ECS Express/FastAPI, RDS/pgvector, private S3, Google OAuth/Calendar, OpenAI, CloudWatch 기준으로 다시 그려야 한다는 수정 조건을 확정했다.

이 과정은 생성 결과를 그대로 채택하지 않고 저장소 구현과 대조해 오류를 발견한 사례다. 현재 `docs/system-architecture.png`는 제출용 최종 도식으로 간주하지 않는다.

## 6. 시행착오에서 얻은 판단 기준

- 로컬 build 성공, CI 성공, 클라우드 배포 성공은 서로 다른 완료 조건이다.
- 외부 서비스 오류는 애플리케이션 오류와 분리해 재현하고, 상태와 로그로 근거를 확인한다.
- 권한 문제를 해결할 때 관리형 광범위 권한을 급히 붙이기보다 실패한 API와 resource condition만 허용한다.
- RAG는 벡터 DB 보유 여부보다 “검색 결과가 생성 입력과 결과 근거로 실제 사용되는가”가 중요하다.
- 사용 권리가 불분명한 데이터는 대회용이라는 이유만으로 수집하지 않는다.
- AI가 만든 화면·도식·코드는 반드시 현재 저장소와 실제 실행 환경을 기준으로 다시 검증한다.
- 체험 모드는 심사 편의를 높이지만, 실제 API/DB/배포 경계와 혼동되지 않도록 문서에서 구분한다.

## 7. 제출 전 남은 작업

1. 최종 PPT/PDF를 `presentation/`에 업로드한다.
2. Amplify에 `main`과 `influence-fe`를 연결하고 `NEXT_PUBLIC_API_URL`을 배포 API로 설정한다.
3. Amplify URL을 백엔드 CORS와 S3 CORS에 반영하고 프론트 → API → RDS/S3 전체 smoke test를 수행한다.
4. 현재 로컬 변경 중인 S3 업로드 개선을 main에 반영한 뒤 실제 AWS presigned PUT 1건을 검증한다.
5. 실제 시스템과 사용자 흐름에 맞는 아키텍처 이미지로 `docs/system-architecture.png`를 교체한다.
